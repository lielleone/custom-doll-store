# Doll store website

> Public portfolio copy. Customer photos (static/images) are replaced by an illustration of the story doll, the contact details in app.py are example values, and the gallery alt texts describe the illustration. The rules below are the ones used while building the real site.


Custom-made plush dolls based on a child's drawing or photo.
Base price 380 NIS, shipping included. Embroidery +30 NIS.
One size only (about 30 to 35 cm). The giant size is not offered because the supplier cannot make it; new orders are always stored with size "standard". Old orders may still have size "giant", so admin.py and mailer.py keep its label.

## Stack
- Backend: Python Flask. app.py, blueprints in orders.py and admin.py, mailer.py (new-order email to the owner).
- Database: SQLite file orders.db. Uploaded drawings are stored in uploads/. Both live in DATA_DIR (default: the project folder).
- Frontend: Jinja templates in templates/, Tailwind built locally into static/css/tailwind.css (see "CSS (Tailwind)" below), components sticker, btn, nav-link, field in static/src/input.css. Hebrew, right-to-left.
- Run: source venv/bin/activate, then python app.py. Site at http://127.0.0.1:5001 (port 5001 because macOS uses 5000 for AirPlay).
- Debug is off by default. For local development only: FLASK_DEBUG=1 python app.py. Never set FLASK_DEBUG=1 on the live server.
- Production: do not use python app.py. The host's WSGI server imports the Flask object from app.py (see "Deployment"). On a server without one, gunicorn -w 2 -b 127.0.0.1:5001 app:app also works. Neither runs the __main__ block, so debug stays off.
- SESSION_COOKIE_SECURE=1 makes the session cookie HTTPS-only. Off by default so local http works. Must be set to 1 on the live server (HTTPS).
- Admin login: after 5 wrong passwords from one IP in 15 minutes, login is blocked for that IP (status 429). Admin session expires 8 hours after login.
- SITE_URL (optional, for example https://example.com, no trailing slash) is the public address of the site. When set, indexable pages get a canonical link and Open Graph tags (share preview, image static/images/main_image.jpeg). Empty by default, then no absolute-URL tags are output. Set it on the live server. It also turns on /sitemap.xml (home, /order, /contact; 404 when empty) and the Sitemap line in /robots.txt. robots.txt always disallows /admin and /thanks.
- Favicon is an inline SVG data URI (teddy bear emoji) in base.html. When CSP is added, allow img-src data:.
- Security headers are added to every response in app.py (SECURITY_HEADERS). No Content-Security-Policy yet (see "CSS (Tailwind)" below).

## CSS (Tailwind)
- Tailwind CLI v3.4.17 (standalone) is at tools/tailwindcss. tools/ is ignored by git; it is not deployed.
- Rebuild after any change to classes in templates/ or to static/src/input.css:
  ./tools/tailwindcss -c tailwind.config.js -i static/src/input.css -o static/css/tailwind.css --minify
- static/css/tailwind.css is committed and served by the site. Whenever classes in templates change, rebuild it and commit it in the same commit, or the new classes will have no style on the live site.
- base.html links it with static_url() from app.py, which adds ?v=<modification time> so browsers load the new file after a rebuild.
- The custom <style> blocks in base.html (fonts, background dots, bubbles, float animation) are not part of the build.
- The Tailwind CDN script is gone, so a Content-Security-Policy header can now be considered. It still has to allow Google Fonts (fonts.googleapis.com styles, fonts.gstatic.com fonts), the two inline <script>s (the "js" class in <head>, the menu) and inline <style> blocks and style attributes in base.html, and img-src data: for the favicon. Not added yet. All scripts are local (static/vendor, static/js), so script-src 'self' plus the menu script is enough.

## Home page story (scrollytelling)
- The first section of templates/index.html (#story): a child's crayon cat sketch that turns into the felt doll while scrolling, then crossfades to the felt cat in main_image.jpeg. It keeps the page's only h1, the intro text and the order button.
- Files: templates/partials/story_cat.svg (the drawing, decorative, aria-hidden), static/js/story.js (the GSAP timeline), story CSS at the end of static/src/input.css (rebuild Tailwind after changes).
- GSAP 3.15.0 is vendored in static/vendor/gsap (gsap, ScrollTrigger, DrawSVGPlugin, MorphSVGPlugin; Standard no-charge license; README has the source and SHA-256 hashes). Only index.html loads it, through {% block scripts %} in base.html. To upgrade: download the new files, check the hashes, update the README.
- Without JavaScript, or with prefers-reduced-motion, story.js does nothing and the section is the normal hero (photo, h1, text, button). Keep it that way.
- The drawing is generated by static/src/story_cat.py: venv/bin/python static/src/story_cat.py > templates/partials/story_cat.svg. Do not hand-edit the SVG; the element ids are used by story.js.
- The story holds the three "how it works" steps; the old separate "איך זה עובד" section was removed (the menu link goes to /#story, and the delivery-time line moved to the order section at the bottom of the home page). Without JS or with reduced motion the steps are listed under the intro. base.html adds class "js" on <html> with a one-line inline script so the list does not flash before the animation; story.js removes it when it does not animate.
- Timeline: at 0% the notebook rests tilted on a desk (perspective, slight blur on desktop, desk shadow). 0-28%: the camera dives in (the page flattens, comes into focus and zooms in to at most 112%, less where the screen is short: zoomScale() in story.js keeps it inside the frame and above the text on phones) while it is coloured; step 1 from 13%. 34-48%: steps back to 100%, pattern and felt pieces; step 2 from 45% (joining and sewing); depth about 72-90%; step 3 from 86% (real photo). Section height 420vh on desktop, 320vh on phones. The floating background bubbles and stickers fade to 18% while the story is on screen and come back after it.
- The stage was checked to fit from 375x667 to 1440x900. After layout changes, check a short phone (375x667) again.

## Gallery and order form (interactive)
- Rule for all of these: progressive enhancement. Without JavaScript every page must still work as a plain page (links, the one-page order form with a visible send button). JS only adds to it. Respect prefers-reduced-motion.
- Gallery (index.html, static/js/gallery.js): each photo is a link to the full image; with JS it opens in a <dialog> (Esc, backdrop or סגירה closes, focus returns), cards rise in on scroll, and a soft tilt with a light sheen follows a mouse (not on touch). No category filter: with two photos of one kind of doll there are no real categories. Add one only when there are real groups of photos.
- Order form (order.html, static/js/order.js, loads gsap + DrawSVG): with JS a 3-step wizard (drawing, options, details and send). Same field names as before; the server is unchanged and still validates everything.
  - Drawing workshop: drop zone, local preview (nothing is uploaded before sending), scan and stitch effect. Client checks mirror the server (JPG/PNG/PDF, 10 MB) and use the server's Hebrew messages; empty required fields use "יש למלא את השדה: <label>".
  - Embroidery is two radio cards with name "embroidery" (value "yes" or empty). The felt patch preview is marked המחשה בלבד; do not present it as the real result.
  - After a server error the wizard starts at step 1, because the browser drops the chosen file.
  - The send button (שליחת ההזמנה לסדנה) plays a short stitch and stamp, then sends; it is disabled meanwhile to prevent double orders.
- Honeypot: keep it clipped in place (1px, clip-path). An offset like left:-9999px makes RTL pages scroll sideways on phones.

## Deployment
Target: PythonAnywhere (WSGI host, behind the host's reverse proxy, HTTPS). The host's WSGI file adds the project folder to sys.path and does: from app import app as application. Install packages there with pip install -r requirements.txt.

Environment variables (put them in the .env next to app.py on the server; never commit it):
- APP_ENV: set to production on the live server. The app then refuses to start if SECRET_KEY, ADMIN_PASSWORD_HASH, SESSION_COOKIE_SECURE, SITE_URL or FLASK_DEBUG is unsafe, and lists every problem.
- SECRET_KEY: required. Random, at least 32 characters, for example from python -c "import secrets; print(secrets.token_hex(32))".
- ADMIN_PASSWORD_HASH: required for admin login. Werkzeug hash of the admin password (generate_password_hash), never the password itself.
- SESSION_COOKIE_SECURE: 1 on the live server (HTTPS-only session cookie). Unset locally.
- SITE_URL: public https:// address, no trailing slash. Turns on canonical, Open Graph, sitemap.xml and the robots.txt Sitemap line.
- TRUST_PROXY: number of reverse proxies in front of the app; 1 on PythonAnywhere. 0 or unset: X-Forwarded-* headers are ignored (local development).
- DATA_DIR: folder for orders.db and uploads/, created if missing. On the server use a folder outside the code folder so a new upload of the code never overwrites customer data. Default: the project folder. A relative path is relative to the project folder.
- ORDERS_OPEN: three values.
  - Unset or anything else (empty, 0): CLOSED, pre-launch mode. No order form (POST /order returns 403 and stores nothing), a "coming soon" banner on public pages, noindex and X-Robots-Tag on everything, robots.txt "Disallow: /", no sitemap.
  - preview: PREVIEW, for testing the live site with people who have the link. The real order form works like OPEN (no banner, no closed card), but search engines are kept out like CLOSED (noindex, X-Robots-Tag, robots.txt "Disallow: /", no sitemap). Orders are saved with status "preview" (admin label הזמנת בדיקה), their email subject starts with [בדיקה], and the admin orders list has a button that deletes all of them and their drawings. A real order cannot be changed to "preview".
  - 1: OPEN, orders open and the site is indexable. With APP_ENV=production the app refuses to start while the legal pages are drafts or have [placeholders] (this lock applies only to 1, not to preview).
  Startup prints "Orders: OPEN", "Orders: PREVIEW" or "Orders: CLOSED".
- FLASK_DEBUG: 1 only for local development with python app.py. Never on the live server.
- SMTP_USER: Gmail address that sends the new-order email.
- SMTP_APP_PASSWORD: Gmail app password for SMTP_USER. Without SMTP_USER and SMTP_APP_PASSWORD no email is sent.
- ORDER_EMAIL: address that receives the new-order email. Default: SMTP_USER.

Deploy zip (only committed files; .gitattributes leaves out .claude, CLAUDE.md, tailwind.config.js and static/src; .env, orders.db, uploads/, venv/ and tools/ are never tracked). Commit first, then run in the project folder:
  git archive --format=zip -o doll_store_deploy.zip HEAD

## Launch checklist
None of these is done yet. Open the site for orders only after all of them, in this order:
1. Legal pages reviewed by a professional; [placeholders] in legal.py filled in; LEGAL_DRAFT = False in legal.py (removes the draft banner and noindex).
2. Answer from the Standards Institute of Israel about the toy safety standard.
3. Business registered.
4. Payment connected, and the thank-you page text updated to match.
5. The boy photo re-checked (cartoon character rights, parents' consent).
6. Test orders deleted from the live database: in the admin orders list press מחיקת כל הזמנות הבדיקה (deletes all orders with status "preview" and their drawings). Older test orders with another status must be deleted by hand.
7. SITE_URL set on the live server.
8. Then set ORDERS_OPEN=1 and restart the app (check the log shows "Orders: OPEN"). ORDERS_OPEN is unset (CLOSED) or preview (PREVIEW, for tests with a shared link) until this step. Before opening for real, use the admin clean-up button, then set ORDERS_OPEN=1.

## Rules
- Never read, print or edit .env, orders.db or anything in uploads/. They hold secrets and customer data. Never put secrets in code or in chat.
- Treat all form input as untrusted and validate it on the server.
- All user-facing text is Hebrew, right-to-left. Keep accessibility: labels on fields, visible focus, enough contrast, keyboard navigation.
- Do not add payment code yet. Payment provider and business registration are decided later by the owner.
- Legal pages (terms, cancellation, privacy, accessibility statement) need professional review. Do not claim legal or standards compliance (accessibility level, toy safety standards) that has not been verified.
- Do not add any product safety or standards claim to the site (European or Israeli standard, hypoallergenic, safe for all ages) until the owner has written confirmation from the Standards Institute of Israel or an accredited lab.
- The home page gallery has 2 photos (girl-and-doll, boy-and-doll). group.jpeg was removed because it showed another brand's label and a printed card with an identifiable person's photo; never add photos like that again. Add a stitching close-up or gift box packaging photo only when such photos exist.
- Gallery photos have no visible captions (owner's choice). Keep a short, natural Hebrew alt text on every image for screen readers, without names or identifying anyone.
- Do not add any new photo of an identifiable person to the site without the owner confirming that the parents consented.
- The thank-you page (templates/thanks.html) does not mention payment, because payment is not connected yet. Its text must change when payment is connected.
- Legal pages /terms, /cancellation, /privacy, /accessibility: texts in legal.py, one template templates/legal.html, links in the footer. They are drafts: LEGAL_DRAFT = True in legal.py shows the draft banner and adds noindex. Text in [square brackets] is a placeholder for the owner. Set LEGAL_DRAFT = False only after professional review.
- Contact details in the SITE dict in app.py are real (phone, WhatsApp, email). The owner has no social media accounts, so the site has no social handle or social links.
- Work in small steps. Before a big change, show a short plan and wait for approval. Commit to git after each finished step with a clear message.
- Reply to the user in Hebrew, short and simple. The user is a student who knows Python but is new to web deployment.
